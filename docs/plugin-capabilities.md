# Plugin Capabilities

What the runtime supports, and how a processor opts into each feature. The
plugins under `internal/validation/` exercise every item here and pass the
Steinberg validator in extensive mode (`just validate-vst3 <validator>`) and,
as CLAP plugins, clap-validator (`just validate-clap <clap-validator>`) and,
as Audio Units, Apple's auval in strict mode (`just validate-au`).

| Plugin type | Bus template | Validation plugin |
| --- | --- | --- |
| Audio effect (mono/stereo, surround) | `bus.NewEffectStereo`, `NewSurround5_1Effect`, `NewMultiChannelEffect` | `gain` |
| Sidechain effect, lookahead/latency | `bus.NewEffectStereoSidechain` | `ducker` |
| Instrument (synth, sampler, drums) | `bus.NewGenerator` | `synth` |
| MIDI effect (arpeggiator, transposer) | `bus.NewMIDIEffect` | `midifx` |
| Analyzer/meter | `bus.NewAnalyzer` + read-only parameters | `gain` (meter) |
| Multi-output (crossover, drum outs) | `bus.NewCrossover`, `NewSplitter`, `WithAuxOutput` | — |

## Building a plugin

A plugin is a `main` package that registers itself:

```go
func init() { plugin.Register(myPlugin{}) }
func main() { standalone.Main() } // runs only in standalone application builds
```

`vst3go new [-type effect|instrument|midi] <dir> <Name>` creates such a
package as its own module (with `main_test.go` using `pkg/plugintest` and
`vst3go` as a `tool` dependency), and `go tool vst3go build [-format
vst3,clap,au,app] [-install] <package> <Name>` builds it, from any module:

- `vst3`: a macOS (`Contents/MacOS`) or Linux (`Contents/<arch>-linux`)
  bundle built with `-buildmode=c-shared`, with
  `Contents/Resources/moduleinfo.json` (VST 3.7 module info, generated by
  loading the built binary with `scripts/moduleinfo.c`).
- `clap`, `au`: the same binary as a CLAP plugin and (macOS) Audio Unit.
- `app`: the standalone application.

`-install` copies the plugins into the user folders
(`~/Library/Audio/Plug-Ins/{VST3,CLAP,Components}`, `~/.vst3`, `~/.clap`).
`-id` (the bundle identifier), `-version` and `-tags` set the bundle details
and build tags; tags in `GOFLAGS` are kept. In this repository
`scripts/build_{vst3,clap,au,standalone}.sh` (`just vst3`, `just clap`, ...)
run the command for one format. Windows uses the mingw cross build
(`scripts/docker_build_windows.sh`) or `scripts/build_windows_vst3.sh`.

One binary can hold several plugins: call `plugin.Register` once per plugin
(each with its own `Info.ID`); the factory lists every class.

The same binary is also a CLAP plugin: it exports `clap_entry` next to
`GetPluginFactory`. `vst3go build -format clap` packages it as a macOS `.clap` bundle or a Linux
`.clap` shared object; the Windows cross build writes `<name>.clap` DLLs. See
[CLAP](#clap) for how the runtime maps onto CLAP.

On macOS it is an Audio Unit (AUv2) as well: `vst3go build -format au`
writes a `.component` bundle
with one component per registered plugin. See [Audio Units](#audio-units).

It also builds as a standalone application: `vst3go build -format app`. See
[Standalone applications](#standalone-applications).

`plugin.Info.Category` selects the host category, for example
`CategoryFxEQ`, `CategoryFxDynamics` or `CategoryInstrumentSynth`; combine
several with `|`.

## Testing plugins

`pkg/plugintest` runs a plugin in `go test` without a host, through the same
runtime a VST3 host drives (lifecycle, sample-accurate automation, MIDI
controller mapping, programs, smoothing, state, presets):

```go
func TestSynth(t *testing.T) {
	p := plugintest.New(t, synthPlugin{})
	p.Note(0, 69, 1, 300, 0)                                  // A4 at sample 300
	p.SendController(0, plugin.MIDIControllerPitchBend, 0, 1) // via IMidiMapping
	p.Automate(paramCutoff, 1000, 0.25)                       // sample-accurate
	out := p.RenderSilence(48000, 0, 2)
	if f := plugintest.ZeroCrossingFrequency(out[0][1000:], 48000); ... {}
}
```

- `plugintest.New` creates and activates an instance (`plugin.OfflineSetup`
  for sample rate, block size, 64-bit, process mode); `Render`,
  `RenderSilence`, `ProcessBuses` (sidechains, aux outputs), `Process64` and
  `ProcessEvents` (MIDI effects) process buffers of any length in host-sized
  blocks, filling buses the test leaves out with silence.
- `Transport` sets tempo and play state; it advances while playing.
- `OutputEvents`, `OutputParameters` (meters), `Latency`, `TakeRestarts` and
  `TakeMessages` expose what the plugin reported; `State`/`SetState` round
  trip state.
- Signal helpers (`Sine`, `Impulse`, `Constant`, `Silence`) and analysis
  (`Peak`, `RMS`, `PeakDB`, `FirstNonZero`, `ZeroCrossingFrequency`).

`plugin.Offline` is the same engine without `testing`, for offline
renderers and batch tools. Each plugin in `internal/validation` has tests
written this way.

## Processing model

`ProcessAudio(ctx)` runs on the audio thread. It must not lock, block or do I/O.

- **Buses.** `ctx.Input`/`ctx.Output` are the main buses.
  `ctx.InputBus(i)`/`ctx.OutputBus(i)` reach every bus, `ctx.Sidechain()` the
  first aux input. An inactive or unconnected bus has no channels.
- **Sample-accurate automation.** The runtime splits the host block at
  parameter change offsets, so `ctx.Param`/`ctx.ParamPlain` always hold the
  value valid for the current segment. `ctx.NumSamples()` is the segment
  length and `ctx.BlockOffset()` its start inside the host block.
- **Events** keep their host-block offsets: inside a segment, the sample index
  of an event is `int(event.Offset) - ctx.BlockOffset()`.
  `ctx.GetAllInputEvents()` returns the segment's events in order.
- **Smoothing.** Give a parameter a ramp time with
  `param.New(...).Smooth(seconds)` (linear: gain, mix, pan) or
  `.SmoothMultiplicative(seconds)` (frequencies, times). `ctx.Smoothed(id)`
  returns its `*param.Ramp` in plain units, retargeted at every segment start;
  advance it with `Next()` per sample, `Fill(buf)` or `Skip(n)`. Ramps keep
  running across segments and blocks and restart at the current value when
  processing starts. `param.NewRamp` is available for DSP-internal values.
- **Silence flags.** `ctx.InputSilenceFlags(bus)` reports silent input channels;
  `ctx.SetOutputSilenceFlags(bus, mask)` tells the host an output is silent.
- **Output parameters** (meters, gain reduction): `ctx.SetOutputParameter(id, normalized)`
  on a `ReadOnly()` parameter. The value goes to the host and the editor.
- **Transport.** `ctx.Transport` carries tempo, time signature, musical position,
  cycle and play/record state; each field group has a `Has*` validity flag.
- **Offline rendering.** `ctx.ProcessMode` is `ProcessModeRealtime`,
  `ProcessModePrefetch` or `ProcessModeOffline`.
- **64-bit processing.** Implement `DoublePrecisionProcessor` and return true
  from `SupportsDoublePrecision()`. When the host picks 64-bit,
  `ctx.Is64Bit()` is true and the audio is in `ctx.Input64`/`ctx.Output64`
  (`InputBus64`, `OutputBus64`, `Sidechain64`); `ctx.Input`/`ctx.Output` are
  nil. A generic helper (`func apply[T float32 | float64](in, out [][]T)`)
  keeps one DSP path for both, see `internal/validation/gain`.
- The audio thread path is allocation-free: events, parameter changes and
  segment views reuse buffers sized at `setupProcessing`.

## MIDI and notes

Input events arrive as `midi.Event` values (a plain struct, no allocation);
`Type` selects the meaningful fields:

- `EventTypeNoteOn`/`EventTypeNoteOff`: `Note`, 0-1 `Velocity`
  (`Velocity7()` for 7 bits), `Tuning` (cents), `Length` and the host `NoteID`
  (`midi.NoteIDNone` when unassigned). Match note-offs on `NoteID` when both
  sides carry one.
- `EventTypePolyPressure`, `EventTypeNoteExpression` (float `Value`, types
  `midi.NoteExpressionVolume`, `...Tuning`, `...Brightness`, ...),
  `EventTypeNoteExpressionInt` (`IntValue`) and `EventTypeNoteExpressionText`
  (UTF-8 `Data`, e.g. phonemes).
- `EventTypeChord` (`Root`, `Bass`, `Mask`, name in `Data`) and
  `EventTypeScale` (`Root`, `Mask`, name in `Data`) from the host chord track.
- `EventTypeSysEx` with the complete message in `Data`.

`Data` of input events is only valid during the `ProcessAudio` call; copy it
to keep it.

VST3 hosts do not send MIDI CC, pitch bend or channel aftertouch as events.
Two ways to receive them:

- `MIDIControllerProcessor.MIDIControllerChannels() int` — the runtime maps
  every controller to a hidden parameter (IDs from `MIDIControllerParamIDBase`)
  and turns its changes back into sample-accurate `EventTypeControlChange`,
  `EventTypePitchBend` (-1..+1) and `EventTypeChannelPressure` input events.
  Plugin parameter IDs must stay below `MIDIControllerParamIDBase`.
- `MIDIMappingProcessor.MIDIControllerParameter(bus, channel, cc)` — map a
  controller straight to one of your parameters (mod wheel to vibrato depth).
  These mappings take precedence. Controller numbers are 0-127 plus
  `MIDIControllerAfterTouch` (128) and `MIDIControllerPitchBend` (129).
- `MIDI2MappingProcessor` maps MIDI 2.0 RPN/NRPN controllers (`IMidiMapping2`).
- `MIDILearnProcessor`/`MIDI2LearnProcessor` receive the controller the user
  moves in the host's MIDI learn mode (`IMidiLearn`/`IMidiLearn2`). Update the
  mapping and call `Host.RestartComponent(RestartMidiCCAssignmentChange)`.

MIDI program changes reach the plugin through the program list (see below),
not as events.

Output events: `ctx.AddOutputEvent(event)` with an event output bus, built with
`midi.NoteOn(...)`, `midi.ControlChange(...)`, `midi.SysEx(data)`, ... and
`.At(offset)`. Notes, poly pressure, note expression (float, int, text) and
SysEx go out as VST3 events; CC, pitch bend, channel pressure and program
change go out as legacy MIDI CC events. Get SysEx/text payload memory from
`ctx.EventDataBuffer(n)`/`ctx.AppendEventText(utf16)` to stay allocation-free.
Chord and scale events are input-only.

## Instruments: note expression, MPE and articulations

- `NoteExpressionProcessor.NoteExpressions(bus, channel)` advertises per-note
  expressions (`INoteExpressionController`). Cubase only sends note
  expression to plugins that do. `NoteExpressionInfo.Format`/`Parse` convert
  values for the host's display.
- `PhysicalUIMappingProcessor` maps MPE dimensions (X/Y movement, pressure) to
  note expression types (`INoteExpressionPhysicalUIMapping`).
- `KeyswitchProcessor` publishes articulation keyswitches
  (`IKeyswitchController`) for host expression maps.

## Presets

`pkg/preset` reads and writes VST3 preset files (`.vstpreset`), the format
hosts use in their preset browsers:

- `Host.SavePreset(path)` writes the current state (parameters and
  `StatefulProcessor` data) with plugin name and category meta info;
  `Host.LoadPreset(path)` restores a preset of this plugin, updates the host
  and the editor, and in distributed plugins the other side.
- `preset.UserDir(vendor, name)` is the per-user folder where hosts look for
  a plugin's presets; `preset.List`, `preset.Save` and `preset.PathFor` manage
  it. The built-in editor has a preset bar on top of these.
- `preset.Decode`/`File.Encode` and `preset.MetaInfo` handle the file format
  directly (factory content tools, converters).

Presets written by `pkg/preset` load with the VST3 SDK's `PresetFile` and vice
versa (`just validate-vst3`).

## Programs and units

- `ProgramListProcessor.ProgramList()` publishes factory presets in the host
  program menu (`IUnitInfo`, `IProgramListData`). The runtime adds a list
  parameter `ProgramParamID` flagged `kIsProgramChange`; selecting a program
  from the host, automation or a MIDI program change loads its values
  (sample-accurately on the audio thread, with a parameter refresh on the
  controller). Parameters missing from `Program.Values` get their defaults;
  read-only and bypass parameters are untouched. `Program.PitchNames` names
  notes (drum pads, keyswitches). Restoring a project restores the selection
  without re-applying the program over the saved values.
- `UnitProcessor.Units()` groups parameters (`param.Parameter.UnitID`); unit 0
  is the root and owns the program list.

## Bus layouts

- Configure buses with `bus.NewBuilder()` or a template. Main buses come first,
  then aux buses. Main buses are reported active by default, aux buses are
  enabled by the host on demand.
- Set an explicit speaker layout with `WithAudioInputArrangement`/`WithAudioOutputArrangement`
  (`bus.Arrangement51`, `bus.Arrangement71Cine`, ...).
- Accept other layouts from the host by implementing
  `BusArrangementProcessor.AcceptBusArrangements(inputs, outputs) bool`.
  When it returns true the runtime updates the bus configuration and channel
  counts before processing starts.

## Latency and tail

- `GetLatencySamples()` reports processing latency (lookahead, linear-phase
  filters). After it changes, call `Host.RestartComponent(plugin.RestartLatencyChanged)`
  from a non-audio thread.
- `GetTailSamples()` reports the decay after input stops; return
  `plugin.TailInfinite` for generators that never decay.

## Host interaction

Implement `HostAwareProcessor.SetHost(plugin.Host)` to talk back to the host
(from the UI/main thread only):

- `EditParameter(id, normalized)` — plugin-side parameter changes (preset
  loads, MIDI learn, custom controls) recorded by the host as an edit.
- `BeginEdit(id)`/`EndEdit(id)` — bracket a continuous change (a drag) so the
  host records one automation pass and one undo step; `EditParameter` calls
  in between are steps of that gesture. The built-in editor does this for
  slider drags.
- `RestartComponent(flags)` — ask the host to re-read latency, parameter
  values/titles, I/O layout, MIDI assignments, note expressions or keyswitches.
- `SendMessage(id, data)` — message the other side of a distributed plugin.

`ChannelInfoProcessor.SetChannelInfo` receives the host channel name, color and
position (`IInfoListener`).

## Distributed processor/controller

By default the processor and controller are one object (single component).
Implement `DistributedPlugin` and return true from `Distributed()` to expose a
separate processor class (`kDistributable`) and controller class, so hosts can
run them in different processes. Each side gets its own `CreateProcessor()`
instance:

- the processor side runs `Initialize`, `SetActive` and `ProcessAudio`;
- the controller side only serves parameters, the editor and the controller
  interfaces;
- parameter values and state reach the controller through the host. `Host`
  calls on the processor side (`RestartComponent`, `EditParameter`) are
  forwarded to the controller; anything else goes through `Host.SendMessage`
  and `MessageReceiver.ReceiveMessage`. Message IDs starting with `vst3go.`
  are reserved.

See `internal/validation/ducker`.

## Editor

The web editor runs in WKWebView on macOS and WebView2 on Windows. On Linux it
is a WebKitGTK view embedded into the host's X11 window, opt-in with the
`webkitgtk` build tag (needs `libwebkit2gtk-4.1-dev`):

```bash
go tool vst3go build -tags webkitgtk ./myplugin MyPlugin
```

It pumps GTK from the host's `IRunLoop` timer. Without the tag Linux builds
have no editor view.

The same views serve VST3 (`IPlugView`) and CLAP (the `gui` extension, see
[CLAP](#clap)). `scripts/check_macos_editor.sh` and
`scripts/docker_check_linux_editor.sh` open the gain and synth editors in a
real window in both formats and check the page <-> Go bridge both ways.

Processors replace the built-in page with their own (`EditorProcessor`,
`plugin.Editor{HTML, Width, Height, Min/Max sizes, FixedSize}`). Every page
gets the `window.vst3go` SDK: live parameters with edit gestures, presets,
`resize`, and custom messages with the processor (`vst3go.send` ->
`EditorMessageProcessor`, `Host.PostEditorMessage` -> `vst3go.on`).
`plugin.EditorBindings` / `WriteEditorBindings` generate typed TypeScript
parameter bindings, and `plugintest.EditorBindings` keeps them current. See
[`web-editor-bridge.md`](web-editor-bridge.md).

## Parameters and state

- `param.Choice` creates list parameters (`IsList`, `N-1` steps); stepped
  parameters snap to their steps when denormalized, matching the VST3 rule.
- `param.BypassParameter` is flagged `IsBypass` so hosts link it to their
  bypass switch.
- Without a custom parser, string-to-value parsing accepts the formatted
  display text ("-6.0 dB", "Q: 0.71", "-∞ dB").
- Parameter values are persisted automatically. Implement `StatefulProcessor`
  for extra state (sample paths, wavetables, sequencer patterns).

## CLAP

A CLAP instance runs the same runtime as a single-component VST3 instance;
processors need no CLAP-specific code.

- The CLAP plugin ID is `Info.ID`; features come from `Info.Category`
  (`Fx|EQ` becomes `audio-effect`, `equalizer`; `Instrument|Synth` becomes
  `instrument`, `synthesizer`; `Fx|Instrument` becomes `note-effect`).
  Implement `plugin.CLAPFeaturesPlugin` to set them explicitly.
- Parameters use plain values: continuous parameters range over `Min..Max`,
  stepped ones over the step index `0..StepCount`. Value text is the
  formatter output plus the unit. Read-only (output) parameters such as
  meters are not exposed: CLAP hosts treat values that change on their own
  as errors. They still reach the editor and VST3 hosts.
- Audio buses are audio ports (64-bit when the processor supports double
  precision); event buses are note ports with the CLAP and MIDI dialects.
- CLAP notes become `midi.Event` notes. Notes without a host note ID get a
  generated one, and wildcard note-offs and expressions (key, channel or
  note ID -1) resolve against the sounding notes. CLAP note expressions map to
  VST3 types (volume, pan, tuning, vibrato, expression, brightness); pressure
  becomes poly pressure. Raw MIDI 1.0 controllers go through the same MIDI
  mapping as on VST3 hosts (`MIDIMappingProcessor`,
  `MIDIControllerProcessor`); program changes select a program.
- `Host.EditParameter`/`BeginEdit`/`EndEdit` become CLAP gesture and value
  events in the next process or flush call; `RestartComponent` maps to
  parameter rescans, latency changes and restart requests. Track name and
  color reach `ChannelInfoProcessor`; program pitch names are CLAP note names.
- Output constant flags come from `ctx.SetOutputSilenceFlags`.
- The editor is the `gui` extension, embedded only, with the platform's
  window API (`cocoa`, `win32`, `x11` in `webkitgtk` builds); builds without
  an editor view do not offer it. On Linux the view's timer runs on the host's
  `timer-support`. Host automation reaches the open page from the main thread
  (`request_callback`), as do state loads, preset loads and program changes.
- Presets: the preset discovery factory has one provider per plugin that
  declares the `.vstpreset` file type and, once it exists, the plugin's user
  preset folder (the one the editor's preset browser and VST3 hosts use).
  Presets are reported with their CLAP and VST3 plugin IDs, modification
  time, musical instrument/style/character tags as features and the other
  meta info attributes as extra info. The `preset-load` extension loads a
  file and reports `loaded` or `on_error` to the host; a loaded preset of
  the user folder becomes the editor's current preset.

`scripts/validate_clap.sh <clap-validator> [out]` builds every validation
plugin as `.clap`, runs clap-validator and then
`internal/validation/hostcheck/clapcheck.c`, which checks sample-accurate
automation, 64-bit audio, notes without IDs, wildcards, note expressions,
raw MIDI, MIDI effect output, programs, note names, latency, state and
preset discovery. Both run with `HOME` in a scratch folder: clapcheck saves
a preset into the user preset folder there, which clap-validator's
`preset-discovery-*` tests then crawl and load.

## Audio Units

On macOS every plugin binary also contains an AUv2 component factory
(`VST3GoAUFactory`, `pkg/plugin/au_darwin.c`). Each Audio Unit instance
hosts one instance of the plugin's own CLAP entry, so it runs the same
runtime and threading as a CLAP host; processors need no AU-specific code.

- Component codes: the type follows the buses and category (`aufx`
  effects, `aumf` effects with note input, `aumu` instruments, `augn`
  generators, `aumi` MIDI processors without audio). The manufacturer code
  is the first four letters of the vendor (first one upper case) and the
  subtype a hash of `Info.ID`; implement `plugin.AudioUnitPlugin` to set
  both (four ASCII characters; Apple reserves all-lowercase manufacturer
  codes). Hosts identify presets and sessions by these codes, so keep them
  stable once released. `vst3go build` writes them into the
  bundle's `Info.plist` by loading the built binary (`scripts/auinfo.c`).
- Audio: CLAP audio ports are AU elements (main bus first, side chains
  and aux outputs after it) with the port's channel count, 32-bit float
  non-interleaved. Inputs are pulled from render callbacks or connections;
  an unconnected side chain is silent. Multi-output plugins render every
  bus in the first `AudioUnitRender` call of a time stamp.
- Parameters are the CLAP parameters with their plain values (stepped ones
  as indexed values with value strings); text comes from the formatter in
  both directions. `AudioUnitScheduleParameters` events reach the
  processor at their buffer offsets (a ramp as its start and end values),
  `AudioUnitSetParameter` changes at the start of the next block (at once
  while the unit is uninitialized); editor edits and gestures reach AU
  parameter listeners (`AUEventListener`) from the main thread.
- State: `kAudioUnitProperty_ClassInfo` holds the plugin state under the
  standard preset keys; factory programs are the factory presets
  (`kAudioUnitProperty_FactoryPresets`, `PresentPreset`).
- MIDI: `MusicDeviceMIDIEvent`/`SysEx` with sample offsets in; the
  plugin's MIDI and note output go to the host's MIDI output callback.
- Host transport (`HostCallbacks`: tempo, beat, time signature, play,
  record, cycle) becomes `ProcessContext` transport. Latency and tail are
  reported in seconds; a latency change while initialized reactivates the
  plugin and notifies the host. Bypass (effects) passes the main input
  through; offline rendering sets the CLAP render mode.
- Editor: `kAudioUnitProperty_CocoaUI` names a view factory class in the
  bundle; the editor follows host resizes within its limits and
  `vst3go.resize`. `vst3go build` names that Objective-C class after
  the bundle (`VST3GO_AU_VIEW_CLASS`) so several vst3go Audio Units can share
  a host process; Audio Units built without it share the default class
  name.

`scripts/validate_au.sh [out]` builds every validation plugin as a
`.component`, installs them as `vst3go-check-*.component` into
`~/Library/Audio/Plug-Ins/Components` (removed on exit), runs `auval
-strict -r 2` on each and then `internal/validation/hostcheck/aucheck_darwin.m`:
parameter text round trips, ClassInfo save/restore and rejection of foreign
state, effect output following a parameter, instrument notes and factory
presets, transposed MIDI output of the MIDI processor, side chain ducking
and latency, and the editor (view factory loaded from the bundle, page
edits reaching AU listeners and `AudioUnitGetParameter`, host changes
reaching the page, the synth page resizing its view).

## Standalone applications

`pkg/standalone` runs the plugin as an application with audio and MIDI
devices, its editor in a window, and its state kept between runs. The plugin
package's `main` calls `standalone.Main()`; plugin builds (c-shared) never
run it, and executables built without the `standalone` tag only print how
to build one. `vst3go build -format app` builds with that tag (plus the
tags in `GOFLAGS`, e.g. `-tags=webkitgtk` for the Linux editor): a macOS
`.app` bundle (with a microphone usage description) or a Linux executable;
the Windows cross build writes `<name>.exe`.

The application hosts the plugin through the plugin's own CLAP entry, so
it runs the same runtime and threading a CLAP host does.

- Audio: miniaudio (`github.com/gen2brain/malgo`) with Core Audio, WASAPI,
  DirectSound, ALSA, PulseAudio, JACK or the `null` device (a timer, for
  tests and servers). One duplex device: the main input bus reads the input
  device (a mono device feeds every channel; `-input none` opens none), the
  main output bus plays on the output device (a mono plugin plays on every
  channel). Other buses get silence. Plugins without audio output (MIDI
  effects) run on a silent stereo output device as their clock.
- MIDI: Core MIDI, the ALSA sequencer and WinMM (`internal/midiport`).
  Channel messages from every input (or the ones named), and on macOS and
  Linux from a virtual input named after the plugin, reach the plugin's
  first note port; its MIDI output can go to a port (`-midi-out`). SysEx
  and real-time messages are dropped.
- Editor: the plugin's `gui` extension in a window (Cocoa, Win32, X11 in
  `webkitgtk` builds), resizable within the editor's limits and following
  `vst3go.resize`. Builds without an editor view, `-headless` and Linux
  without an X server run without a window.
- Settings and state: device choices go to `standalone.json` and the plugin
  state to `standalone.state` in `<user config dir>/<vendor>/<name>`
  (`-config` sets another directory). Flags given on the command line
  override and update the saved settings; the state loads at launch
  (`-reset` skips it) and saves on quit (window closed, Cmd+Q, SIGINT,
  SIGTERM, `-duration` elapsed).
- Restarts: a plugin that changes its latency or ports while active is
  deactivated and reactivated with the device stopped.

```text
-list                 list audio devices and MIDI ports
-plugin id|name       the plugin to run when the binary registers several
-backend name         coreaudio, wasapi, dsound, winmm, alsa, pulseaudio, jack, oss, null
-output / -input name audio devices (exact name or a unique part; -input none)
-sample-rate hz       0: the device rate
-buffer frames        device period (default 256)
-midi-in list         all (default), none, or comma-separated port names
-midi-out name        MIDI output port
-virtual-midi=false   no virtual MIDI input
-headless             no editor window
-config dir, -reset, -duration d
```

`scripts/check_standalone.sh` runs the `pkg/standalone` tests (an
instrument and an effect through the host glue, the null device, settings
and state files), every validation plugin as an application on the null
device, `internal/validation/hostcheck/standalonecheck` (a MIDI round trip
through the transpose plugin over virtual MIDI ports: in, plugin, out) and
on macOS the synth's editor window following its page's resize.
`scripts/docker_check_linux_standalone.sh` covers Linux: headless apps,
the synth editor under Xvfb (window resized to 720x420 by the page) and,
with `SOUND=1`, playback through ALSA.

## Known limits

- Windows builds are compile- and export-checked (`scripts/docker_build_windows.sh`);
  they are not run through the validator in CI. Follow `docs/windows-validation.md`
  on a real machine.
- `moduleinfo.json` is generated by native builds only, not by Windows cross
  builds.
- In distributed mode, program data written by the host through
  `IProgramListData` updates the processor side only.
- Chord and scale events are input-only; the Linux editor needs an X11 host
  (no Wayland embedding exists in VST3).
- Audio Units are AUv2 only (no AUv3 app extension), with the channel
  configuration of the CLAP ports (no host-negotiated layouts) and no
  MIDI 2.0 event lists.
- Standalone applications have no in-app audio settings dialog (devices are
  chosen with flags and remembered), no transport (the plugin gets no
  tempo or position), and Windows builds are compile-checked only; the
  Linux MIDI and Windows MIDI/audio paths have not run on real hardware
  here (Core MIDI, Core Audio and ALSA playback have).
- CLAP editors cannot float in a plugin-owned window, and CLAP hosts have no MIDI learn mode,
  keyswitch or note expression metadata queries; distributed plugins run as
  one CLAP object, so `Host.SendMessage` returns an error there.
