# Plugin Capabilities

What the runtime supports, and how a processor opts into each feature. The
plugins under `internal/validation/` exercise every item here and pass the
Steinberg validator in extensive mode (`just validate-vst3 <validator>`).

| Plugin type | Bus template | Validation plugin |
| --- | --- | --- |
| Audio effect (mono/stereo, surround) | `bus.NewEffectStereo`, `NewSurround5_1Effect`, `NewMultiChannelEffect` | `gain` |
| Sidechain effect, lookahead/latency | `bus.NewEffectStereoSidechain` | `ducker` |
| Instrument (synth, sampler, drums) | `bus.NewGenerator` | `synth` |
| MIDI effect (arpeggiator, transposer) | `bus.NewMIDIEffect` | `midifx` |
| Analyzer/meter | `bus.NewAnalyzer` + read-only parameters | `gain` (meter) |
| Multi-output (crossover, drum outs) | `bus.NewCrossover`, `NewSplitter`, `WithAuxOutput` | — |

## Building a plugin

A plugin is a `main` package that registers itself:

```go
func init() { plugin.Register(myPlugin{}) }
func main() {}
```

`scripts/build_vst3.sh <package> <Name> [out]` (or `just vst3 <package> <Name>`)
builds a macOS (`Contents/MacOS`) or Linux (`Contents/<arch>-linux`) bundle with
`-buildmode=c-shared` and writes `Contents/Resources/moduleinfo.json` (VST 3.7
module info, generated by loading the built binary with `scripts/moduleinfo.c`).
Windows uses `scripts/build_windows_vst3.sh`.

One binary can hold several plugins: call `plugin.Register` once per plugin
(each with its own `Info.ID`); the factory lists every class.

`plugin.Info.Category` selects the host category, for example
`CategoryFxEQ`, `CategoryFxDynamics` or `CategoryInstrumentSynth`; combine
several with `|`.

## Testing plugins

`pkg/plugintest` runs a plugin in `go test` without a host, through the same
runtime a VST3 host drives (lifecycle, sample-accurate automation, MIDI
controller mapping, programs, smoothing, state, presets):

```go
func TestSynth(t *testing.T) {
	p := plugintest.New(t, synthPlugin{})
	p.Note(0, 69, 1, 300, 0)                                  // A4 at sample 300
	p.SendController(0, plugin.MIDIControllerPitchBend, 0, 1) // via IMidiMapping
	p.Automate(paramCutoff, 1000, 0.25)                       // sample-accurate
	out := p.RenderSilence(48000, 0, 2)
	if f := plugintest.ZeroCrossingFrequency(out[0][1000:], 48000); ... {}
}
```

- `plugintest.New` creates and activates an instance (`plugin.OfflineSetup`
  for sample rate, block size, 64-bit, process mode); `Render`,
  `RenderSilence`, `ProcessBuses` (sidechains, aux outputs), `Process64` and
  `ProcessEvents` (MIDI effects) process buffers of any length in host-sized
  blocks, filling buses the test leaves out with silence.
- `Transport` sets tempo and play state; it advances while playing.
- `OutputEvents`, `OutputParameters` (meters), `Latency`, `TakeRestarts` and
  `TakeMessages` expose what the plugin reported; `State`/`SetState` round
  trip state.
- Signal helpers (`Sine`, `Impulse`, `Constant`, `Silence`) and analysis
  (`Peak`, `RMS`, `PeakDB`, `FirstNonZero`, `ZeroCrossingFrequency`).

`plugin.Offline` is the same engine without `testing`, for offline
renderers and batch tools. Each plugin in `internal/validation` has tests
written this way.

## Processing model

`ProcessAudio(ctx)` runs on the audio thread. It must not lock, block or do I/O.

- **Buses.** `ctx.Input`/`ctx.Output` are the main buses.
  `ctx.InputBus(i)`/`ctx.OutputBus(i)` reach every bus, `ctx.Sidechain()` the
  first aux input. An inactive or unconnected bus has no channels.
- **Sample-accurate automation.** The runtime splits the host block at
  parameter change offsets, so `ctx.Param`/`ctx.ParamPlain` always hold the
  value valid for the current segment. `ctx.NumSamples()` is the segment
  length and `ctx.BlockOffset()` its start inside the host block.
- **Events** keep their host-block offsets: inside a segment, the sample index
  of an event is `int(event.Offset) - ctx.BlockOffset()`.
  `ctx.GetAllInputEvents()` returns the segment's events in order.
- **Smoothing.** Give a parameter a ramp time with
  `param.New(...).Smooth(seconds)` (linear: gain, mix, pan) or
  `.SmoothMultiplicative(seconds)` (frequencies, times). `ctx.Smoothed(id)`
  returns its `*param.Ramp` in plain units, retargeted at every segment start;
  advance it with `Next()` per sample, `Fill(buf)` or `Skip(n)`. Ramps keep
  running across segments and blocks and restart at the current value when
  processing starts. `param.NewRamp` is available for DSP-internal values.
- **Silence flags.** `ctx.InputSilenceFlags(bus)` reports silent input channels;
  `ctx.SetOutputSilenceFlags(bus, mask)` tells the host an output is silent.
- **Output parameters** (meters, gain reduction): `ctx.SetOutputParameter(id, normalized)`
  on a `ReadOnly()` parameter. The value goes to the host and the editor.
- **Transport.** `ctx.Transport` carries tempo, time signature, musical position,
  cycle and play/record state; each field group has a `Has*` validity flag.
- **Offline rendering.** `ctx.ProcessMode` is `ProcessModeRealtime`,
  `ProcessModePrefetch` or `ProcessModeOffline`.
- **64-bit processing.** Implement `DoublePrecisionProcessor` and return true
  from `SupportsDoublePrecision()`. When the host picks 64-bit,
  `ctx.Is64Bit()` is true and the audio is in `ctx.Input64`/`ctx.Output64`
  (`InputBus64`, `OutputBus64`, `Sidechain64`); `ctx.Input`/`ctx.Output` are
  nil. A generic helper (`func apply[T float32 | float64](in, out [][]T)`)
  keeps one DSP path for both, see `internal/validation/gain`.
- The audio thread path is allocation-free: events, parameter changes and
  segment views reuse buffers sized at `setupProcessing`.

## MIDI and notes

Input events arrive as `midi.Event` values (a plain struct, no allocation);
`Type` selects the meaningful fields:

- `EventTypeNoteOn`/`EventTypeNoteOff`: `Note`, 0-1 `Velocity`
  (`Velocity7()` for 7 bits), `Tuning` (cents), `Length` and the host `NoteID`
  (`midi.NoteIDNone` when unassigned). Match note-offs on `NoteID` when both
  sides carry one.
- `EventTypePolyPressure`, `EventTypeNoteExpression` (float `Value`, types
  `midi.NoteExpressionVolume`, `...Tuning`, `...Brightness`, ...),
  `EventTypeNoteExpressionInt` (`IntValue`) and `EventTypeNoteExpressionText`
  (UTF-8 `Data`, e.g. phonemes).
- `EventTypeChord` (`Root`, `Bass`, `Mask`, name in `Data`) and
  `EventTypeScale` (`Root`, `Mask`, name in `Data`) from the host chord track.
- `EventTypeSysEx` with the complete message in `Data`.

`Data` of input events is only valid during the `ProcessAudio` call; copy it
to keep it.

VST3 hosts do not send MIDI CC, pitch bend or channel aftertouch as events.
Two ways to receive them:

- `MIDIControllerProcessor.MIDIControllerChannels() int` — the runtime maps
  every controller to a hidden parameter (IDs from `MIDIControllerParamIDBase`)
  and turns its changes back into sample-accurate `EventTypeControlChange`,
  `EventTypePitchBend` (-1..+1) and `EventTypeChannelPressure` input events.
  Plugin parameter IDs must stay below `MIDIControllerParamIDBase`.
- `MIDIMappingProcessor.MIDIControllerParameter(bus, channel, cc)` — map a
  controller straight to one of your parameters (mod wheel to vibrato depth).
  These mappings take precedence. Controller numbers are 0-127 plus
  `MIDIControllerAfterTouch` (128) and `MIDIControllerPitchBend` (129).
- `MIDI2MappingProcessor` maps MIDI 2.0 RPN/NRPN controllers (`IMidiMapping2`).
- `MIDILearnProcessor`/`MIDI2LearnProcessor` receive the controller the user
  moves in the host's MIDI learn mode (`IMidiLearn`/`IMidiLearn2`). Update the
  mapping and call `Host.RestartComponent(RestartMidiCCAssignmentChange)`.

MIDI program changes reach the plugin through the program list (see below),
not as events.

Output events: `ctx.AddOutputEvent(event)` with an event output bus, built with
`midi.NoteOn(...)`, `midi.ControlChange(...)`, `midi.SysEx(data)`, ... and
`.At(offset)`. Notes, poly pressure, note expression (float, int, text) and
SysEx go out as VST3 events; CC, pitch bend, channel pressure and program
change go out as legacy MIDI CC events. Get SysEx/text payload memory from
`ctx.EventDataBuffer(n)`/`ctx.AppendEventText(utf16)` to stay allocation-free.
Chord and scale events are input-only.

## Instruments: note expression, MPE and articulations

- `NoteExpressionProcessor.NoteExpressions(bus, channel)` advertises per-note
  expressions (`INoteExpressionController`). Cubase only sends note
  expression to plugins that do. `NoteExpressionInfo.Format`/`Parse` convert
  values for the host's display.
- `PhysicalUIMappingProcessor` maps MPE dimensions (X/Y movement, pressure) to
  note expression types (`INoteExpressionPhysicalUIMapping`).
- `KeyswitchProcessor` publishes articulation keyswitches
  (`IKeyswitchController`) for host expression maps.

## Presets

`pkg/preset` reads and writes VST3 preset files (`.vstpreset`), the format
hosts use in their preset browsers:

- `Host.SavePreset(path)` writes the current state (parameters and
  `StatefulProcessor` data) with plugin name and category meta info;
  `Host.LoadPreset(path)` restores a preset of this plugin, updates the host
  and the editor, and in distributed plugins the other side.
- `preset.UserDir(vendor, name)` is the per-user folder where hosts look for
  a plugin's presets; `preset.List`, `preset.Save` and `preset.PathFor` manage
  it. The built-in editor has a preset bar on top of these.
- `preset.Decode`/`File.Encode` and `preset.MetaInfo` handle the file format
  directly (factory content tools, converters).

Presets written by `pkg/preset` load with the VST3 SDK's `PresetFile` and vice
versa (`just validate-vst3`).

## Programs and units

- `ProgramListProcessor.ProgramList()` publishes factory presets in the host
  program menu (`IUnitInfo`, `IProgramListData`). The runtime adds a list
  parameter `ProgramParamID` flagged `kIsProgramChange`; selecting a program
  from the host, automation or a MIDI program change loads its values
  (sample-accurately on the audio thread, with a parameter refresh on the
  controller). Parameters missing from `Program.Values` get their defaults;
  read-only and bypass parameters are untouched. `Program.PitchNames` names
  notes (drum pads, keyswitches). Restoring a project restores the selection
  without re-applying the program over the saved values.
- `UnitProcessor.Units()` groups parameters (`param.Parameter.UnitID`); unit 0
  is the root and owns the program list.

## Bus layouts

- Configure buses with `bus.NewBuilder()` or a template. Main buses come first,
  then aux buses. Main buses are reported active by default, aux buses are
  enabled by the host on demand.
- Set an explicit speaker layout with `WithAudioInputArrangement`/`WithAudioOutputArrangement`
  (`bus.Arrangement51`, `bus.Arrangement71Cine`, ...).
- Accept other layouts from the host by implementing
  `BusArrangementProcessor.AcceptBusArrangements(inputs, outputs) bool`.
  When it returns true the runtime updates the bus configuration and channel
  counts before processing starts.

## Latency and tail

- `GetLatencySamples()` reports processing latency (lookahead, linear-phase
  filters). After it changes, call `Host.RestartComponent(plugin.RestartLatencyChanged)`
  from a non-audio thread.
- `GetTailSamples()` reports the decay after input stops; return
  `plugin.TailInfinite` for generators that never decay.

## Host interaction

Implement `HostAwareProcessor.SetHost(plugin.Host)` to talk back to the host
(from the UI/main thread only):

- `EditParameter(id, normalized)` — plugin-side parameter changes (preset
  loads, MIDI learn, custom controls) recorded by the host as an edit.
- `BeginEdit(id)`/`EndEdit(id)` — bracket a continuous change (a drag) so the
  host records one automation pass and one undo step; `EditParameter` calls
  in between are steps of that gesture. The built-in editor does this for
  slider drags.
- `RestartComponent(flags)` — ask the host to re-read latency, parameter
  values/titles, I/O layout, MIDI assignments, note expressions or keyswitches.
- `SendMessage(id, data)` — message the other side of a distributed plugin.

`ChannelInfoProcessor.SetChannelInfo` receives the host channel name, color and
position (`IInfoListener`).

## Distributed processor/controller

By default the processor and controller are one object (single component).
Implement `DistributedPlugin` and return true from `Distributed()` to expose a
separate processor class (`kDistributable`) and controller class, so hosts can
run them in different processes. Each side gets its own `CreateProcessor()`
instance:

- the processor side runs `Initialize`, `SetActive` and `ProcessAudio`;
- the controller side only serves parameters, the editor and the controller
  interfaces;
- parameter values and state reach the controller through the host. `Host`
  calls on the processor side (`RestartComponent`, `EditParameter`) are
  forwarded to the controller; anything else goes through `Host.SendMessage`
  and `MessageReceiver.ReceiveMessage`. Message IDs starting with `vst3go.`
  are reserved.

See `internal/validation/ducker`.

## Editor

The web editor runs in WKWebView on macOS and WebView2 on Windows. On Linux it
is a WebKitGTK view embedded into the host's X11 window, opt-in with the
`webkitgtk` build tag (needs `libwebkit2gtk-4.1-dev`):

```bash
GOFLAGS=-tags=webkitgtk scripts/build_vst3.sh ./myplugin MyPlugin
```

It pumps GTK from the host's `IRunLoop` timer. Without the tag Linux builds
have no editor view.

## Parameters and state

- `param.Choice` creates list parameters (`IsList`, `N-1` steps); stepped
  parameters snap to their steps when denormalized, matching the VST3 rule.
- `param.BypassParameter` is flagged `IsBypass` so hosts link it to their
  bypass switch.
- Without a custom parser, string-to-value parsing accepts the formatted
  display text ("-6.0 dB", "Q: 0.71", "-∞ dB").
- Parameter values are persisted automatically. Implement `StatefulProcessor`
  for extra state (sample paths, wavetables, sequencer patterns).

## Known limits

- Windows builds are compile- and export-checked (`scripts/docker_build_windows.sh`);
  they are not run through the validator in CI. Follow `docs/windows-validation.md`
  on a real machine.
- `moduleinfo.json` is generated by native builds only, not by Windows cross
  builds.
- In distributed mode, program data written by the host through
  `IProgramListData` updates the processor side only.
- Chord and scale events are input-only; the Linux editor needs an X11 host
  (no Wayland embedding exists in VST3).
