# 런타임 계약

이 저장소는 재사용 가능한 VST3 바인딩과 런타임 계층, `ProcessAudio` 안에서 쓰는 DSP 라이브러리, 그리고 이 둘 위에 만든 쇼케이스 플러그인을 제공합니다. 제품 전용 로직(라이선스, 인스톨러, 브랜딩)은 사용하는 쪽 프로젝트에 둡니다.

## 패키지 범위

다운스트림 프로젝트는 다음 패키지를 지원되는 API 범위로 취급해야 합니다:

- `pkg/plugin`
- `pkg/vst3`
- `pkg/midi`
- `pkg/framework/bus`
- `pkg/framework/param`
- `pkg/framework/plugin`
- `pkg/framework/process`
- `pkg/framework/state`
- `pkg/preset`
- `pkg/plugintest`
- `pkg/audiofile`
- `pkg/standalone`
- `pkg/dsp/...`
- `pkg/framework/dsp`
- `pkg/framework/voice`
- `pkg/framework/debug`
- `pkg/ara`

`pkg/plugin`의 C 브리지 소스, 임베디드 에디터 에셋, 플랫폼별 에디터 shim은 이 API 범위를 뒷받침하며 직접 호출하지 않습니다.

`pkg/dsp`의 DSP 프로세서는 오디오 스레드 밖(생성자나 `Initialize`)에서 만들고 크기를 정하며, 샘플/버퍼 단위 메서드는 메모리를 할당하지 않으므로 `ProcessAudio`에서 안전하게 호출할 수 있습니다. 각 인스턴스는 하나의 프로세서가 소유하며 동시에 사용하기에 안전하지 않습니다. `pkg/dsp/analysis`의 미터와 스코프는 다른 스레드에서도 읽습니다. `Get*` 메서드는 어느 고루틴에서 호출해도 안전하고 `Process`를 기다리게 하지 않으며(값은 트리플 버퍼링으로 넘겨집니다), `Process`, `Reset`, 설정 메서드는 오디오 스레드에서 호출합니다.

## 라이프사이클 기대 사항

- `plugin.Plugin`은 팩토리입니다. `CreateProcessor`는 래퍼 인스턴스마다 새로운 프로세서 인스턴스를 반환해야 합니다.
- `plugin.Processor.Initialize`는 블록 크기와 샘플 레이트에 의존하는 상태를 준비합니다.
- `plugin.Processor.SetActive(true)`는 이후 메모리 할당에 민감한 추가 설정 없이도 프로세서가 실시간 작업을 수행할 수 있는 상태가 되도록 해야 합니다.
- `plugin.Processor.ProcessAudio`는 정상 동작 중에 반복 호출되는 오디오 콜백이며, 피할 수 있는 메모리 할당과 블로킹 작업은 피해야 합니다.
- `plugin.Processor.SetActive(false)`는 트랜스포트 상태, 대기 중인 이벤트, 스무딩 상태 및 그 밖의 런타임 전용 캐시를 리셋하는 경계입니다.
- `plugin.StatefulProcessor`는 선택 사항이며, 파라미터 값만으로는 프로세서 동작을 복원하기에 충분하지 않을 때에만 구현해야 합니다.
- `Initialize`는 host가 컴포넌트를 초기화할 때 한 번 실행되고, 이후 `setupProcessing`이 호출될 때마다 host의 샘플 레이트와 블록 크기로 다시 실행됩니다. 버스 배치는 `SetActive(true)`가 호출되는 시점에 확정됩니다.
- 선택적 host 기능(64비트 처리, 버스 배치, MIDI 매핑/learn, 노트 익스프레션, 키스위치, 프로그램, 유닛, 채널 정보, host 메시지)은 프로세서에서 선택적으로 구현하는 인터페이스이며, `docs/plugin-capabilities.md`에 설명되어 있습니다.
- `plugin.Register`는 플러그인마다 한 번씩 호출할 수 있으며, 하나의 바이너리가 여러 플러그인을 제공할 수 있습니다.
- `DistributedPlugin`에는 플러그인 인스턴스마다 프로세서 인스턴스가 두 개 생성됩니다. 프로세서 쪽은 위의 라이프사이클을 실행하고, 컨트롤러 쪽은 파라미터, 에디터, 컨트롤러 쿼리만 담당하며 `Initialize`, `SetActive`, `ProcessAudio`는 호출되지 않습니다.
- CLAP 인스턴스는 동일한 라이프사이클로 프로세서 하나를 실행합니다. CLAP `init`은 `Initialize`를 호출하고, `activate`는 host의 샘플 레이트와 최대 블록 크기로 `Initialize`를 다시 호출한 뒤 `SetActive(true)`를 호출하며, `deactivate`는 `SetActive(false)`를 호출합니다. 오디오 스레드에서 호출되는 CLAP `reset`은 재할당 없이 `SetActive(false)`와 `SetActive(true)`를 호출합니다. `DistributedPlugin`은 하나의 CLAP 객체로 실행됩니다.
- Audio Unit 인스턴스(macOS)는 CLAP 인스턴스 하나를 호스팅합니다. `AudioUnitInitialize`는 출력 샘플 레이트와 슬라이스당 최대 프레임 수로 이를 활성화하고, 그 이후의 첫 번째 렌더에서 처리가 시작됩니다. `AudioUnitUninitialize`는 이를 중지하고 비활성화하며, `AudioUnitReset`은 CLAP `reset`을 호출합니다. 렌더, 파라미터 flush, 재활성화는 하나의 락으로 직렬화되며, 플러그인 콜백(`request_callback`, 파라미터 리스너를 위한 편집, 에디터 크기 조정)은 메인 디스패치 큐에서 실행됩니다.
- LV2 인스턴스(Linux)는 CLAP 인스턴스 하나를 호스팅합니다. `activate`는 인스턴스화 시점의 샘플 레이트와 `bufsz:maxBlockLength`(옵션이 없으면 4096)에 맞춰 이를 활성화하고, 첫 번째 `run`에서 처리가 시작되며, `deactivate`는 이를 중지하고 비활성화합니다. `run`은 오디오 스레드이며, 인스턴스화, 활성화, 상태 호출, UI의 idle 콜백은 메인 스레드로 취급되고, 플러그인의 `request_callback` 작업은 idle 콜백에서(그리고 활성화 및 상태 호출 전후에) 실행됩니다. 재시작 요청(레이턴시 변경)은 다음 `run`의 시작 시점에 플러그인을 다시 활성화합니다.
- 스탠드얼론 애플리케이션(`pkg/standalone`)은 자체 플러그인을 위한 CLAP host입니다. 프로세스당 인스턴스는 하나이며, 오디오 장치의 샘플 레이트와 period로 활성화되고, 플러그인이 재시작을 요청하면 비활성화되었다가 다시 활성화됩니다. 메인 스레드는 메인 고루틴이며(이 패키지는 `init`에서 이를 프로세스 메인 스레드에 고정합니다), 이 고루틴이 창과 이벤트 루프를 실행합니다. 오디오 장치의 스레드는 `process`를 실행합니다.

- ARA 플러그인(`plugin.ARAPlugin`)은 host가 만드는 문서 컨트롤러마다 `ara.Document`와 컨트롤러를 하나씩 받습니다. 문서는 플러그인 인스턴스와 무관하게 host가 파괴할 때까지 유지됩니다. 인스턴스는 최대 하나의 문서에 바인딩되고(`ARAProcessor.BindARA`, host는 인스턴스를 활성화하기 전에 한 번 바인딩합니다), 파괴될 때 바인딩이 풀리며, 문서와의 파괴 순서는 어느 쪽이든 됩니다.

## 스레드 안전성 기대 사항

- `pkg/framework/param.Registry`의 조회는 락을 잡지 않습니다. 변경되지 않는 스냅샷을 읽고, 등록은 새 스냅샷을 게시합니다. 개별 파라미터 값은 atomic입니다.
- 오디오 경로는 런타임이 다른 곳에서 잡는 락을 잡지 않습니다. 모든 host 진입점의 호출별 인스턴스 조회는 변경되지 않는 스냅샷을 읽고, CLAP에서 플러그인 쪽 편집은 락 없는 큐로 `process`에 전달됩니다.
- `pkg/framework/process.Context`는 한 번에 하나의 처리 패스가 소유하며, 워커 고루틴 간에 동시에 공유해서는 안 됩니다.
- `ProcessAudio`는 host 오디오 스레드에서 실행되며, 그 밖의 모든 `Processor` 메서드(MIDI learn, 채널 정보, `ReceiveMessage` 포함)와 모든 `Host` 호출은 host/UI 스레드에서 실행됩니다. 런타임은 인스턴스별로 host 스레드의 라이프사이클 호출을 직렬화합니다. CLAP에서는 `Host`를 통한 편집이 큐에 쌓였다가 다음 `process` 또는 `flush` 호출에서 host에 보고됩니다.
- 런타임은 각 host 블록을 파라미터 변경 오프셋에서 분할하고 구간마다 `ProcessAudio`를 한 번씩 호출하므로, 프로세서는 한 번의 호출 안에서는 파라미터 값이 일정하다는 점을 전제로 할 수 있습니다.
- `pkg/framework/state.Manager`는 직렬화 헬퍼이며, 동시에 실행되는 실시간 오디오 경로가 아니라 host 상태 콜백에서 호출해야 합니다.
- ARA 모델 호출(문서 편집, 아카이빙, 콘텐츠 리더, `Binding` 역할 변경)은 ARA가 요구하는 대로 host의 메인 스레드에서 실행됩니다. 플러그인 컨트롤러 메서드와 `ara.Document`를 다루는 에디터 코드도 그 스레드에서 실행됩니다. 분석은 오디오 소스마다 별도 goroutine에서 실행됩니다. 오디오 스레드에서 `Binding.Playback`과 `RegionPlayback` 메서드는 원자적 스냅샷과 메모리에 있는 소스 샘플을 읽으며, host의 오디오 리더는 호출하지 않습니다.
- 플랫폼 에디터 브리지는 Go 측 파라미터 모델을 단일 진실 공급원(source of truth)으로 취급해야 하며, 병렬 상태를 직접 변경하는 대신 UI 변경을 일반적인 파라미터 업데이트 흐름을 통해 되돌려 전달해야 합니다.

## 실시간 동작

런타임 쪽 처리는 메모리를 할당하지 않고 락도 잡지 않지만, Go 런타임 위에서 돌기 때문에 하드 실시간 보장은 없습니다. 가비지 컬렉터의 stop-the-world 구간에 Go로 들어오는 호출은 그 구간이 끝날 때까지 기다립니다. 이 구간은 짧고(1ms 미만) 힙 크기에 비례해 늘지 않으므로, 플러그인의 나머지 부분의 할당률을 적당히 유지하고 `just rtcheck`로 측정하세요. 이 명령은 일반적인 이펙트 체인을 (host처럼) 네이티브 실시간 스레드에서 호출하는 동안 다른 고루틴이 메모리를 할당하게 하고, 예산을 넘긴 블록이 있으면 실패합니다. Apple M4에서 48 kHz, 128샘플 블록(예산 2.67 ms)으로 측정했을 때 가장 긴 호출은 가비지가 없을 때 0.87 ms, 초당 1 GB를 할당할 때(20초 동안 GC 56회) 1.11 ms였고, 예산을 넘긴 블록은 없었습니다.

런타임은 이런 정지가 드물게 일어나도록 하기도 합니다. Go 자체의 페이싱에서는 힙이 4 MB 최소치부터 두 배가 될 때마다, 그리고 적어도 2분마다 컬렉터가 실행되므로, 에디터나 파라미터 텍스트의 작은 할당만으로도 몇 분마다 실행됩니다. 첫 인스턴스가 만들어질 때 vst3go는 비율 기반 페이싱을 끄고, 살아 있는 힙에 여유분(`plugin.DefaultGCHeadroom`, 64 MB; 살아 있는 힙이 더 크면 그 크기)을 더한 메모리 한도를 설정하며 이 한도는 매 사이클 뒤에 옮겨집니다. 그래서 컬렉터는 바이너리가 지난 사이클 이후 그만큼 할당한 뒤에만 실행됩니다. 인스턴스를 활성화할 때 지난 사이클 이후 1 MB 넘게 할당되어 있으면 먼저 수집하므로, 인스턴스를 만들고 로드하며 생긴 가비지는 첫 블록 전에 정리됩니다. 대가는 최대 여유분만큼의 추가 메모리입니다. `plugin.SetGCHeadroom(bytes)`(`init`에서 호출)로 바꿀 수 있고 0이면 Go의 페이싱으로 돌아가며, 환경 변수 `VST3GO_GC_HEADROOM`(바이트), `GOGC`, `GOMEMLIMIT`가 우선합니다. `just rtcheck`로 초당 1 MB를 60초 동안 할당했을 때 여유분 정책에서는 수집이 한 번도 일어나지 않았고, `GOGC=100`에서는 6번 일어났습니다.

데드라인 가드는 이런 정지가 미치는 영향을 제한하며, 기본으로 켜져 있습니다. `NewBaseProcessor`는 share를 `DefaultProcessDeadline`(0.5)으로 설정하고, `BaseProcessor`를 쓰지 않는 프로세서도 `plugin.DeadlineProcessor`를 구현하지 않으면 같은 값을 받습니다. `SetProcessDeadline(0)`을 호출하면 가드가 꺼지고 블록은 host의 오디오 스레드에서 실행됩니다. 가드가 켜져 있으면 블록은 실시간 워커 스레드(macOS에서는 time-constraint 스레드, Linux에서는 프로세스가 쓸 수 있을 때 `SCHED_FIFO`, Windows에서는 time-critical 우선순위)에서 실행됩니다. 바이너리의 인스턴스들은 이 워커 스레드를 공유합니다. 활성화된 인스턴스마다 워커를 하나씩 풀에 더하므로 처리 중인 블록이 없는 인스턴스는 언제나 빈 워커를 찾습니다. 블록은 호출한 host 스레드가 마지막으로 쓴 워커에게 가고, 워커는 작업 뒤 20µs 동안 스핀하므로 한 스레드에서 여러 인스턴스를 차례로 처리하는 host는 스레드를 깨우는 비용 없이 블록을 넘깁니다. 스레드를 깨우는 데 오래 걸리는 환경(가상 머신은 쉬는 CPU를 1ms 넘게 재우기도 합니다)에서는, 깨어나는 데 데드라인의 4분의 1보다 오래 걸린 워커가 다음 작업 4096개 동안 블록 사이의 간격을 한 번에 최대 6ms까지 스핀하며 기다립니다. 워커는 활성화 때 시작하면서 Go에 한 번 들어가므로, 스레드를 런타임에 묶는 비용을 블록 안에서 치르지 않습니다. 워커와 host 스레드에서 Go로 들어가는 호출은 x86에서 denormal을 0으로 처리(FTZ/DAZ)한 채 실행됩니다. x86에서 denormal 연산은 백 배 느리고, ARM은 제 속도로 처리합니다. host의 오디오 스레드는 C 코드만 실행합니다. 블록을 워커 소유 메모리로 복사하고, 블록 길이의 `share`만큼만 기다린 뒤, 결과를 다시 복사해 옵니다. 처음 30 µs와 데드라인 직전 구간은 스핀으로 기다리고, 그 사이에는 시스템의 타임드 대기가 정확하다고 확인된 만큼만 잠듭니다(첫 가드가 시작될 때와 매번 대기할 때 측정). 그래서 잠이 몇 밀리초씩 늦게 깨는 환경에서도 데드라인에 맞춰 돌아옵니다. 데드라인을 넘긴 블록은 무음을 출력하고 백그라운드에서 마저 처리됩니다. 그동안 도착한 블록도 무음을 출력하며, 그 블록의 노트·MIDI 이벤트(오프셋 0으로 옮김)와 바뀐 파라미터의 마지막 값은 다음에 실행되는 블록으로 넘어갑니다. 한 작업에 다 들어가지 않는 이벤트와 파라미터 변경(VST3 이벤트 2048개나 CLAP 이벤트 4096개, 파라미터 큐 1024개, 포인트 8192개 초과)도 마찬가지로 넘어가므로 잃어버리는 것은 없습니다. 늦은 블록의 출력 이벤트와 출력 파라미터 값은 버려집니다. 오디오 스레드에서 오는 파라미터 flush와 reset도 작업으로 실행되고, 처리 시작·중지는 Go에 들어가지 않으므로 실시간 모드에서 host의 오디오 스레드는 Go 런타임을 기다리지 않습니다. 오프라인 렌더링은 워커가 비면 데드라인 없이 host 스레드에서 실행되며, host 계약을 어긴 블록(플러그인을 설정할 때보다 샘플, 버스, 채널이 많은 블록)도 마찬가지입니다. 이 설정은 플러그인이 활성화될 때 읽히고 VST3, CLAP, AU, LV2와 standalone 애플리케이션에 모두 적용됩니다. 환경 변수 `VST3GO_PROCESS_DEADLINE=<share>`는 프로세스 안의 모든 플러그인에 대해 이 값을 덮어씁니다(`0`이면 끔). share가 0.5면 host는 블록의 나머지 절반을 자기 몫으로 씁니다. LV2에서는 이때 `run`이 Go에 들어가지 않으므로 `plugins.ttl`이 `lv2:hardRTCapable`을 선언합니다. `freewheel` 포트(`lv2:freeWheeling`)는 host가 freewheel하는 동안 플러그인을 오프라인 렌더링으로 바꾸고, 지연 시간 변경은 `run`에서 플러그인을 다시 활성화하지 않고 latency 포트로 알립니다. standalone 애플리케이션의 오디오 콜백은 C(vendored miniaudio)입니다. MIDI 포트가 채우는 링에서 MIDI 입력을 가져오고, 플러그인의 MIDI 출력은 고루틴이 내보내는 링에 남깁니다. `internal/validation/stall`은 60 ms 동안 멈추고, hostcheck, clapcheck, aucheck, lv2check는 호출이 데드라인 안에 무음으로 돌아오는지, 건너뛴 블록의 노트가 나중에 도착하는지 확인합니다. hostcheck와 clapcheck는 한 작업의 용량을 넘는 이벤트가 다음 블록에 도착하는지도, clapcheck는 네 오디오 스레드의 인스턴스 32개가 워커를 공유하고 그사이 인스턴스가 생성·파괴되어도 다른 블록의 오디오를 받지 않는지도, lv2check는 freewheel 중에는 데드라인 없이 렌더링하는지도 확인합니다. 가드와 별개로, Audio Unit 렌더 호출은 메인 스레드를 기다리지 않습니다. 메인 스레드가 렌더 락을 잡고 있는 동안(재초기화하거나 Go로 파라미터를 flush할 때) 그 블록은 무음으로 렌더링됩니다.

## 상태와 영속성

- 파라미터 상태가 기본 영속성 계층입니다.
- `pkg/framework/state.Manager`는 헤더, 버전, 순서대로 나열된 파라미터 값, 선택적 커스텀 페이로드로 이루어진, 이 저장소가 직접 정의한 단순한 바이너리 형식으로 기록합니다.
- 알 수 없는 파라미터 ID는 순방향 호환성(forward compatibility)을 위해 로드할 때 무시됩니다.
- 프로그램 선택기(`plugin.ProgramParamID`)는 다른 파라미터와 마찬가지로 저장되며, 이를 복원해도 복원된 값 위에 프로그램이 다시 적용되지는 않습니다.
- host가 프로그램 목록 슬롯(`IProgramListData`)에 기록하는 프로그램 데이터는 별도의 불투명(opaque) 형식을 사용하며 컴포넌트 상태에 포함되지 않습니다.
- 커스텀 상태는 `StatefulProcessor` 또는 `state.Manager`의 커스텀 저장/로드 훅을 통해서만 추가해야 합니다.
- ARA 플러그인의 문서 데이터(`ModificationArchiver`, `SourceArchiver`, `DocumentArchiver`)는 인스턴스 상태와 별도로 ARA 아카이빙을 통해 host의 곡에 저장되며, `Config.ArchiveID`가 그 형식을 나타냅니다.
- 웹 에디터 스냅샷은 레지스트리 상태를 UI 쪽에 반영한 미러로, 로컬 에디터 복원/하이드레이션에는 유용하지만, host에서 볼 수 있는 플러그인 상태는 여전히 VST3 `GetState` / `SetState` 콜백을 통해 전달되어야 합니다.

## 다운스트림 사용

다운스트림 저장소가 이 포크를 사용할 때는 다음을 따릅니다:

- `github.com/meteuix/vst3go/v2`를 import합니다
- 위에 나열한 지원 패키지를 기반으로 플러그인/런타임 로직을 구축합니다
- 신호 처리에는 `pkg/dsp`를, 참조 플러그인으로는 `examples/`를 사용합니다
- 제품 전용 코드(라이선스, 인스톨러, 브랜딩)는 다운스트림 저장소에 둡니다
- host별 동작, 인스톨러 레이아웃, 서명, DAW 호환성은 다운스트림 저장소에서 검증합니다

태그가 게시되면 다운스트림 저장소는 계속 변하는 브랜치 대신 태그가 지정된 버전에 고정하여, 런타임과 브리지 변경 사항을 신중하게 업그레이드할 수 있도록 해야 합니다.
